**审计对象**：AI 营销战略执行智能体（FastAPI 后端 `src/` + 微信小程序前端 `miniapp/` + `tests/` + 文档/配置）
**审计性质**：只读审计，**未对任何应用文件做任何修改**（仅新增本报告）
**审计日期**：2026-08-10
**审计方式**：逐文件静态阅读 + 文档与代码交叉比对（未运行测试、未部署）

## 0. 总体结论

项目在「诊断 → 7 天计划 → 复盘」的 **Agent 层**有较完整的 mock 测试覆盖，代码可读性与 fallback 设计（3 次重试 + 规则引擎兜底）基本到位。

但以下几个问题足以影响**生产可用性、安全性与可维护性**，按优先级排列：

| 优先级 | 数量 | 代表问题 |
|--------|------|----------|
| **P0（阻塞/高危）** | 4 | 依赖声明缺失导致按官方命令装不上；CORS 通配+凭据；Mock JWT 任意伪造； |
| **P1（严重）** | 5 | 异步框架用同步 DB 阻塞事件循环；上传路径遍历；上传仅扩展名校验；路由遮蔽；用 GitHub PAT 当对称密钥 |
| **P2（中等）** | 6 | 文档/版本/许可证严重漂移；任务模块是 Mock 桩；配置项形同虚设；测试无 DB 隔离；API 层零测试 |
| **P3（轻微）** | 4 | 死代码；弃用 API；dev 依赖冗余；快照机制小缺陷 |

**正面项**：未提交任何真实密钥；全库走 SQLAlchemy ORM 参数化查询（无 SQL 注入面）；`.gitignore` 已覆盖 `.env` 与 `data/app.db`。

## 1. P0 — 阻塞 / 高危

### 1.1 [High] `pyproject.toml` 缺失运行时依赖，按官方推荐命令安装即崩
- **位置**：`pyproject.toml:42-48` vs `requirements.txt:1-22`
- **现象**：`[project].dependencies` 只列了 `fastapi / uvicorn / pydantic / httpx / python-dotenv`，**缺失** `SQLAlchemy`、`aiosqlite`、`openai`、`jinja2`、`python-multipart`。但代码强依赖它们（`db/models.py` 用 SQLAlchemy、`services/llm.py` 用 openai、`prompts/loader.py` 用 jinja2、文件上传需要 python-multipart）。
- **风险**：README 推荐 `pip install -e ".[dev]"` 安装，启动即 `ModuleNotFoundError`。新人按文档无法跑起来。
- **建议**：补齐 dependencies，或明确以 `requirements.txt` 为唯一可信来源并在 README 标注。

### 1.2 [High] CORS `allow_origins=["*"]` + `allow_credentials=True`
- **位置**：`src/api/main.py:45-51`
- **现象**：Starlette 在两者同开时，会将请求方 `Origin` 原样回显，等效于「允许任意站点携带凭据调用本 API」。
- **风险**：典型高危误配置，任何安全扫描器都会标红；一旦未来引入 Cookie/Session 即直接暴露 CSRF/凭据窃取面。当前鉴权走 `Authorization` 头（非 Cookie），危害暂时受限，但仍属禁止项。
- **建议**：显式列出小程序合法域名白名单；生产环境去掉 `allow_credentials=True` 或收窄 origins。

### 1.3 [High] Mock JWT —— 无真实签名，token 可任意伪造
- **位置**：`src/api/auth.py:56-81`；全仓无任何路由对 token 验签
- **现象**：`_generate_mock_jwt` 用常量 `mock_signature` 作签名；`login` 接收 `wx.login()` 的 code 但**从不向微信校验**，直接用 `uuid.uuid4().hex` 生成 user_id。前端把 token 塞进 `Authorization` 头，后端**从不解码/校验**。
- **风险**：任何人可自造任意 `user_id` 的伪 token；所有「鉴权」形同虚设，无法做用户归属与授权。`/api/business`、`/api/review` 等写接口对任何持有 token 的调用者开放。
- **建议**：接入真实 JWT（`jwt.encode`/`decode` + 密钥），并在依赖注入层统一校验；`login` 必须调用 `code2session` 校验微信 code。

### 1.4 [High] 把 GitHub PAT 当作对称密钥使用（密钥管理反模式）
- **位置**：`miniapp/utils/env.ts:1-34`、`scripts/encrypt-prod-url.js:23`、README「生产加密方案」
- **现象**：生产 URL 的「KDF + 三级加密」方案中，Seed 被 README 旧版写成「复用第三方平台 PAT」的形式（如 GitHub Personal Access Token）。
- **风险**：把一个具备 GitHub 账户作用域的凭证用作应用对称密钥，是严重误用——该 Token 一旦泄露，既暴露 GitHub 账户，又直接可还原生产后端域名。种子管理上的攻击面远超方案本身。
- **建议**：改用独立的、与应用无关的随机密钥（如 32 字节随机串），绝不复用任何第三方平台的 PAT。
- **【状态：已于「前端加密漂移清零（任务 5）」中彻底修复】** 整个前端加密方案（`miniapp/utils/env.ts`、`scripts/encrypt-prod-url.js`、全局 `ENCRYPTION_SEED`）已删除；生产 `api_base_url` 不再前端硬编码或加密，改由后端 `POST /api/auth/login`（及 `verify_auth`）在登录成功后于 `AuthResponse.data` 下发，前端存入 Storage（`md:api_base_url`）供 `getBase()` 读取。彻底消除了「把任意第三方 PAT 当作对称密钥」的反模式。

## 2. P1 — 严重

### 2.1 [High] 异步/同步严重错配：所有 async 路由都在用同步 DB 引擎阻塞事件循环
- **位置**：`src/db/models.py:102-112`，并扩散至全部 `src/api/*.py`
- **现象**：`DATABASE_URL` 声明为 `sqlite+aiosqlite:///...`，但 `init_db` 第 105 行把 `+aiosqlite` 替换掉，实际创建同步 `sqlite:///` 引擎（`aiosqlite` 根本没被使用）。每个 `async def` 路由内部 `session = SyncSession()` 都是阻塞调用，在 asyncio 事件循环里串行化所有 DB 操作。
- **风险**：「FastAPI 异步 + aiosqlite」名不副实；并发下吞吐被拖垮甚至超时。
- **建议**：改为 `async_sessionmaker` + `AsyncSession`，或至少用 `run_in_threadpool` 包装同步 DB 调用。

### 2.2 [High] 文件上传仅靠扩展名校验（无 MIME/Magic byte 校验）
- **位置**：`src/api/review.py:350,521`；`src/utils/document_parser.py:38-47`
- **现象**：`is_image_file` 仅比对扩展名集合（`png/jpg/jpeg/webp/bmp/gif`，与 settings 列表还不一致），未校验 `Content-Type`，未读文件头（magic bytes）。
- **风险**：攻击者可上传伪装成 `.png` 的 SVG/HTML/JS；若后续以 `<img>`/直链渲染，可导致存储型 XSS 或 polyglot 攻击。
- **建议**：校验 magic bytes；类型白名单；渲染时强制设置 `Content-Disposition: attachment` 或 `Content-Type: image/*` 并经服务端归一化转码。

### 2.3 [High] 上传文件名拼接存在路径遍历风险
- **位置**：`src/api/review.py:317, 365-367, 526`
- **现象**：`safe_filename = f"{timestamp}_{uuid.uuid4().hex[:8]}_{file.filename}"` 后 `target = UPLOAD_DIR / safe_filename; target.write_bytes(content)`。原始 `file.filename` **原样拼接**。FastAPI 的 `UploadFile.filename` 未必清洗 `../`。
- **风险**：`file.filename` 含 `../../` 时，`Path(UPLOAD_DIR)/"../../etc/passwd"` 在 `write_bytes` 时被 OS 解析到 `UPLOAD_DIR` 之外，攻击者可覆盖进程权限内任意文件。uuid 前缀不能防遍历。
- **建议**：仅保留扩展名并重命名为服务端生成的随机名（`os.path.basename()` 后仍建议丢弃原始名）；写入前 `target.resolve()` 校验仍在 `UPLOAD_DIR` 内。

### 2.4 [Medium] 路由遮蔽：`POST /diagnosis/start` 实际不可达
- **位置**：`src/api/diagnosis.py:165` vs `:239`
- **现象**：`POST /diagnosis/{business_id}`（165 行）先注册，`POST /diagnosis/start`（239 行）后注册。Starlette 按注册顺序匹配，`/diagnosis/start` 会被前者以 `business_id="start"` 截获，且前者无请求体——命中后忽略 JSON body 并因找不到 business 返回 404。
- **风险**：`start_diagnosis_v3` 专用端点永远进不去，属于真实路由 bug。
- **建议**：将字面量路径（如 `/start`）放在带参数的动态路径之前注册，或改用不同前缀（如 `/diagnosis/start/{business_id}`）。

### 2.5 [Medium] 「KDF + 三级加密」是混淆而非加密（安全剧场）
- **位置**：`miniapp/utils/env.ts:30-34`、`:99-245`；`scripts/encrypt-prod-url.js`
- **现象**：KDF 盐值 `MD::env::v3::...` 与算法完全硬编码在前端；`PROD_BASE_URL_CIPHER`、`EXPECTED_KEY_FINGERPRINT` 也硬编码在 `env.ts` 并提交仓库。唯一保密的只有 seed。此外 `env.ts:71-92` 存在一条 **FNV-1a 非加密哈希** 的 fallback 派生路径——在旧客户端上实际用的是非密码学哈希，与脚本端 SHA-256 不一致。
- **风险**：拿到仓库代码者，只要获得 seed 即可还原生产域名；seed 又通过 `globalData`/Storage 注入，本身无保护。README 却把此方案作为安全卖点宣传（「生产敏感配置零明文」「Fail-Fast 安全拦截」），给维护者错误安全感。仅防「肉眼扫描」，无密码学强度。
- **建议**：把它定位为「防误提交」的混淆层，不要宣传为安全控制；同时修复 SHA-256/FNV-1a 两条派生路径不一致的问题（旧端解密会失败或产生弱密钥）。
- **【状态：已于「前端加密漂移清零（任务 5）」中彻底修复】** 前端加密模块 `miniapp/utils/env.ts`（含 `PROD_BASE_URL_CIPHER`、`EXPECTED_KEY_FINGERPRINT`、SHA-256/FNV-1a 派生路径）与 `scripts/encrypt-prod-url.js` 已整体删除，全仓不再有任何前端硬编码密钥/盐值/密文。README 已改写为「后端下发配置（无本地密钥）」方案，不再将前述混淆层宣称为安全控制。

## 3. P2 — 中等

### 3.1 [Medium] 文档/版本/许可证全面漂移
- **版本号五处不一致**：模块 docstring `V3.0.0`（`main.py:3` 等）｜`project-info.json:3` `0.1.0`｜`pyproject.toml:11` `0.3.0`｜`项目开发文档汇总.md:3` `v3.1`｜`settings.py:57` `0.1.0`。
- **README 声称支持 PostgreSQL**（`README.md:86`），代码只有 SQLite（`db/models.py`）。
- **README 技术栈写「通义千问」**（`README.md:98`），实际 `settings.py:40` 用 `gpt-4o`，`project-info.json:21` 也写 GPT-4o。
- **`project-info.json` API/模块清单严重缺失**：实际有 10 个 router（auth/business/dashboard/diagnosis/execution/plan/review/roadmap/task/dashboard），但 project-info 只描述了 business/diagnosis/execution/review 4 个。
- **README 目录结构与真实前端不符**：声称 `pages/ 10 屏`（实际 `app.json` 9 页）、`components/ 10 个`（实际 9 个）、引用 `miniapp/behaviors/user-info.ts`（目录不存在）、引用 `AI营销智能体-微信小程序开发文档.md`/`开发思路文档.md`（文件不存在，真实主文档是 `项目开发文档汇总.md`）。
- **许可证冲突**：`pyproject.toml:15,32` 声明 `MIT`，`README.md:29,367-411` 宣称「Research Only / 非商业需书面授权」——二者互斥，存在法律风险。
- **建议**：统一版本来源（单点定义）、修正 README 模型/数据库/页面数等表述、明确单一致许可。

### 3.2 [Medium] 任务模块为 Mock 桩，与前端页面严重脱节
- **位置**：`src/api/task.py:68-114`（`_get_mock_task_detail` 返回硬编码模板，不查库）、`:241`（`/task/upload` 返回 `file_url="/uploads/task_uploads/..."`）
- **现象**：`/task/detail`、`/task/checkin`、`/task/upload` 都未持久化真实任务状态；且**全仓没有任何静态路由挂载 `/uploads`**，返回的 URL 实际不可访问。
- **风险**：小程序有 task 页面，后端对应功能未真正实现，属「半成品」接口。
- **建议**：补齐任务持久化与静态文件挂载（`StaticFiles`），或在前端标注该模块未就绪。

### 3.3 [Medium] 配置文件与校验逻辑漂移（`allowed_image_types` 从未使用）
- **位置**：`src/config/settings.py:64-69` vs `src/utils/document_parser.py:38-47` vs `src/api/review.py:350`
- **现象**：`settings.allowed_image_types = ["image/png","image/jpeg","image/jpg","image/webp"]` 实际**未被任何上传校验使用**；`review` 用的是 `document_parser.is_image_file`，其接受 `.bmp/.gif`（不在 settings 列表内）；`is_csv_file` 还额外接受 `.tsv`，而 `project-info.json` 的 `doc_types` 只列 `["text/csv"]`。
- **建议**：统一到单一类型白名单来源，消除三处不一致。

### 3.4 [Medium] 测试无 DB 隔离，直接污染真实数据库
- **位置**：`tests/test_pipeline.py:39-61`（用全局 `SyncSession()` 写 `data/app.db`）；`tests/conftest.py` 未覆盖 `DATABASE_URL`
- **现象**：测试向项目真实 `data/app.db` 写数据（虽用 uuid 避免主键冲突，但 review/pipeline 状态会跨运行累积）；CI 多次运行会积脏数据。
- **建议**：用 `tmp_path` 或内存库（`sqlite:///:memory:`）做测试隔离。

### 3.5 [Medium] API 层零测试覆盖（最高价值面未被测）
- **位置**：`tests/` 全量（仅 `test_*_agent.py` / `test_models.py` / `test_prompt_*.py` / `test_pipeline.py`）
- **现象**：10 个 router（CORS、文件上传校验、Mock 认证、business CRUD、上文发现的路由遮蔽、Mock 任务端点）**完全没有测试**。测试只覆盖 agents/models/prompts/pipeline。
- **建议**：为 router 层补 `httpx.ASGITransport` 集成测试，重点覆盖上传/鉴权/路由遮蔽。

### 3.6 [Medium] 多模态 LLM 视觉客户端密钥回退会 401
- **位置**：`src/services/llm.py:73-80`
- **现象**：`api_key = llm_config.vision_api_key or llm_config.text_api_key`。未配 `OPENAI_API_KEY` 时，GPT-4o（vision）请求会拿 DeepSeek 的 key 去打 OpenAI 端点，必然鉴权失败；且 `chat_with_images` 本身无 try/except 兜底。
- **建议**：vision 与 text 的 key 独立校验；缺失时给出明确错误而非静默失败。

## 5. 其他观察

- **LLM 调用层**（正面）：`services/llm.py` 的 `_extract_json` 容错、懒加载客户端、缺失 key 时清晰报错，设计合理。

- **`datetime.utcnow` 等弃用项**见 4.2。
- **复盘数据合并「先到优先」**（`document_parser.merge_parsed_data`）可能静默丢数据：CSV 与截图提供同一指标时，后到者被丢弃且无提示。
